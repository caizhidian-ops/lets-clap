## 合并所有权

- Mio：前置语音交互、宠物孵化、年龄/心情获取、AI 节奏编排与难度调整。
- 我们：游戏场景与动作、拍点判定、游戏结果、试听承接、专辑墙、勋章和现有 3D 资产。
- 共同对齐：宠物 ID、情绪到关卡映射、节奏时间轴、正式音频来源、模型配置、完成/重试/返回导航。
- 原则：一个应用入口、一份会话状态、一套麦克风控制。先用适配层连接，避免直接拼接两份整页 HTML、CSS 与全局状态。

## 建议交接数据

Mio → 游戏：`sessionId, mood, ageRange?, petId, gameId, planId, bpm, expectedOnsetsSec, durationSec, difficulty?, songId?, backingAudioUrl?`。

时间轴使用相对游戏开始的秒数（排除准备倒计时）；实际输入 `times` 延续现有毫秒口径。明确区分背景伴奏与完成后作品音频。

游戏 → 结果：保留现有 `runId, planId, gameId, inputSource, outcome, matchedCount, expectedCount, missedCount, extraCount, durationSec, times`，跳绳另有 `bestCombo`；附带会话、宠物、心情与正式歌曲标识。

现在 `letsclap:completed` 事件是在点击“试听作品”后派发，作品 `id` 等于 `runId`。正式音频已有 `window.LetsClapPlayback.setResult({runId, audioUrl, feedback})`，只接受当前作品，音频需持久 HTTP(S) 地址或同源路径。若 Mio 提前生成音频或离开结果页后回填，应改为按作品 ID 管理异步状态，不能依赖当前 draft。

## 已识别的接口缺口

1. `mountInteriorSession()` 目前只接收 BPM、模式、宠物和回调，主流程固定八拍/十六拍。风车底层引擎支持自定义 onsets，但主入口没有透传；跳绳引擎目前只支持等距拍点。Mio 的动态编排不能直接视为已接入。
2. 渲染层当前风车固定鲸鱼、跳绳固定企鹅，传 petId 并不代表支持任意宠物。孵化结果与场景宠物的对应需要明确。
3. 模型凭据已提供，但 CLI 保存的凭据不会自动进入 Node 服务。当前反馈服务使用 QWEN_API_KEY / DASHSCOPE_API_KEY，固定 DashScope URL；收到 Mio 后核对她的环境变量、模型和 endpoint，服务端接入，不放浏览器或提交 .env。
4. 难度不能只改显示文字；需定义实际拍点、容错窗口、回合长度和成功门槛。首轮可先统一四分音符与支持的 BPM，复杂节奏随后扩展。

## 收到代码后的顺序

1. 在独立目录解包并盘点技术栈、入口、依赖、环境变量名、API、资产和存储键；保留当前改动与历史作品。
2. 分别启动两份应用，确认她实际实现的流程；对照所有权表标出重叠。
3. 确定单一主入口，接入“孵化/语音 → 游戏”的适配层，保留我们的两个关卡。
4. 接通“完成 → 试听 → 收藏 → 刷新后播放”，再接正式音频和模型反馈。模型失败允许重试，保留拍点与作品。
5. 合并验收：平静/开心各完整一轮；麦克风拒绝与模型失败；返回/再玩不重复监听；作品改名与历史数据保留；手机布局；勋章不误解锁。

## 当前验证

本轮使用 bundled Node 执行 `node --test`：19/19 通过。默认非登录 shell 的 Node 不支持 --test，使用 README 指定的 bundled runtime。此轮为代码与单元/HTTP测试盘点，未重跑浏览器、真实麦克风、正式歌曲或真实模型链路；Mio 联合验收待代码到位。
