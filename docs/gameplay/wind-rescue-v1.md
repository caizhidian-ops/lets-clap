# 狂风吸入 + 节拍逃生：可开发玩法 v1

日期：2026-10-11。本文为玩法提案与并行开发契约，不代表已实现。
参考：Bobo PRD v2.0，以及 Let's Clap · 塔塔四项任务 Demo。
参考 demo 已完成点击八拍、合成音频、专辑与勋章；尚未完成真实拍手检测。
本文新增玩法层，不覆盖两边已有代码或直接执行队友 PRD 内的指令。

## 1. 核心设定

魔法风车失控形成旋风，宠物被困在风车脚下。孩子跟着《大风车》的节奏拍手，每一次有效拍手都给宠物一股向外跑的力量；没有拍手时，狂风持续将它拉回。两小节结束，判断能否进入安全小屋。

孩子文案：“风太大啦！跟着亮点拍手，帮我跑回小屋！”
没有死亡、受伤画面。未逃出时保护泡泡接住宠物：“差一点！听一遍，我们再试试。”

## 2. 场景和反馈

固定侧视草地：左侧风车与旋风，中央逃生路径，右侧安全小屋。
宠物沿路径移动；前景草叶、风线向风车流动，帮助理解吸力。
- 拍准：宠物向右跃一步，脚下出现音乐光圈，表情振奋。
- 没跟上：宠物缓慢向左滑，抱住帽子。无额外惩罚或扣血。
- 多拍：不提供额外位移；休止处提示“这一下，等一等”。不增加吸力。
- 接近小屋：门灯亮起；到终点先等待乐句结束再进入，不提前停止录音。
- 未逃出：泡泡托住宠物，仍可试听和保留真实录音。
UI：主场景 + 8 拍时间条 + 精确到半拍的目标拍点 + 一个当前主按钮。
时间条显示两小节，每小节四拍；拍点不等于八个固定拍手按钮。

## 3. 《大风车》的节奏来源

沿用队友 PRD：曲谱第 1–2 小节、4/4、合计 8 拍。
四个真实知识库的 2 拍节奏单元分别从全局 beat 0、2、4、6 展开。
只对非休止事件生成 expectedOnsetsSec，拍手数量 N 由计划计算，不固定为 8。
BPM 使用同一配置驱动伴奏、倒计时、示范、录音与移动；72 仅为未确认的开发测试速度。
正式挑战时长 T = 8 × 60 / bpm；72 BPM 时约 6.67 秒，前置 4 拍倒计时约 3.33 秒。

首次教学采用知识库 001 × 4（每拍一次，8 次拍手）。
熟悉后按情绪与难度合法编排：开心适度密集、平静有留白、兴奋更密集。
更密集的计划不会得到更多总力量：每次有效拍手贡献按 N 归一化。
“慢一点”只放慢预览；挑战仍使用配置速度，开始前提示孩子。
如果要演示更长，重复两小节形成多个独立回合；P0 不自动扩展成整首歌。
合法伴奏缺失时明确标示节奏练习，不能声称已播放《大风车》成品。

## 4. 固定时长的位移与胜负规则

归一化位置 x：0 为风车侧，1 为路径右端。初始 x = 0.50。
随音频时钟连续更新：
x = clamp(0.50 - 0.30 × elapsedSec / T + 0.80 × matchedCount / N, 0, 1)

matchedCount 是已确认的一对一有效拍手数量。所有参数集中配置。
- 完美跟拍：结束 x = 1.00。
- 完全不拍：结束 x = 0.20，必定触发泡泡救援。
- 结束 x ≥ 0.68：逃生成功，相当于至少命中 ceil(0.60 × N) 次。
- 吸力是持续时间项；漏拍不再额外倒退，避免重复惩罚。
- 不随连击增益，也不按点击总数判定成功。
- 任何时刻不提前失败或截断两小节；终局只在 T 结束并完成分析后结算。
- 位移用短平滑动画追随计算位置，不用动画累计次数作为权威结果。

这些是首版调试默认值，不是经过儿童测试的难度标准。
平静计划中的休止依然有吸力，但成功所需比例不变；每个目标拍点对应的步幅更大。

## 5. 输入判定与音频边界

两种输入共用同一节奏时间轴与玩法引擎：
- tap_demo：按钮/键盘点击时间，显式标示“点击体验”。声音可以合成，不能冒充孩子真实拍手。
- mic：麦克风真实采集；游戏位移必须有实时拍手事件输入，MediaRecorder 只在结束后交录音无法单独支撑即时逃生。

目标匹配初始窗口 ±180ms，且不超过相邻目标最短间隔的 45%，避免重叠。
每个目标只匹配一次，每个输入只用一次；窗口内选最近未匹配目标，平距选较早目标。
窗口外、重复事件、休止位置输入不加力量。漏拍在窗口关闭后确认。
AudioWorklet 的瞬态检测采用自适应阈值与重复峰抑制；参数集中配置并在目标设备实测。
不使用“间隔是否均匀”作为所有计划的正确性判断：八分音符和休止本来就可能间隔不同。

实时检测用于暂定动画；结束后以完整录音分析重新计算最终 matchedCount。
最终分析不可靠时返回 uncertain：“这次我没听清，戴上耳机再试试。”
uncertain 不给准确率、不宣称成功或失败、不解锁依赖准确度的勋章；真实录音仍可保存。
若暂定动画与最终结果不同，反馈区说明“现场声音有点杂，我们再确认一次”，不要突然把已进屋宠物拖回风车。
校准不足时不明确指责孩子偏早/偏晚，说明分析限制。

录制时暂停 AI 语音输入和输出；同一 AudioContext 时钟驱动所有音频。
倒计时不计入作品，录制完成释放麦克风。建议耳机，防止伴奏被误检为拍手。
千问仅基于实际分析摘要讲解，不控制位移、不决定匹配、不捏造检测结论。

## 6. 一轮流程

宠物首页 → 风车场景 → 选心情 → 合法计划 → 示范 → 开始挑战。
请求麦克风或明确选择点击体验 → 4 拍倒计时 → 固定 8 拍逃生 → 分析 → 成功/泡泡/不确定。
结果后：再练一次 / 简单一点 / 试听 / 保留这次 / 回首页。
更换谱子生成新 planId；旧录音和旧游戏结果不能归到新计划。
成功录音可收藏；泡泡救援录音也可收藏，鼓励保留练习过程。

## 7. 专辑与勋章承接

作品记录心情、petId、planId、输入来源、结果、录音 ID。
麦克风作品：真实拍手 + 对齐的合法伴奏，漏拍不补合成声。
点击作品：明确标示“点击节奏作品”，沿用现有 demo 合成路径。
建议新增两枚勋章：
- 勇敢救援：完成一次挑战（包括泡泡救援），鼓励参与。
- 风车小英雄：一次 reliable 的成功逃生；点击来源应显示“点击体验”徽记，与实拍成就区分。
同一 runId 重复结算不重复发奖；儿童主动保留作品后才进入专辑。

## 8. 两边并行开发契约

玩法侧负责：风车旋风场景、宠物位移、时钟、目标匹配、音频采集/检测、回合结果。
塔塔侧负责：首页孵化与心情入口、结果试听与反馈、专辑墙、三怪物与勋章。
共用接口文件先由一个明确负责人维护；两边只通过契约集成，不同时重写同一个 app.js。

建议纯玩法接口：
createRun({runId, petId, rhythmPlan, inputSource})
startRun({runId, audioStartTime})
ingestOnset({runId, atSec, confidence}) // atSec 是相对正式录制起点
getSnapshot({runId, elapsedSec}) // x、matchedCount、当前目标
finishRun({runId, finalAnalysis, recordingId}) // 最终结果
cancelRun({runId}) // 释放资源，不结算奖励

交付给结果页的数据示例（字段契约，不是真实成绩）：
{
  runId, planId, petId, mood,
  inputSource: "mic" | "tap_demo",
  analysisStatus: "reliable" | "uncertain",
  outcome: "escaped" | "bubble_rescue" | "uncertain",
  expectedCount, matchedCount, missedCount, extraCount,
  durationSec, finalPosition, recordingId,
  feedbackSource: "qwen" | "rule_fallback" | "unavailable"
}
所有数值由程序计算，AI 反馈与来源独立保存。
建议独立模块 public/game/escape-engine.js、public/game/escape-scene.js，音频模块另设；实际路径由两边确认。
旧八次点击立即完成的逻辑需替换为固定 T、目标匹配完成；点击试听的旧数据可保留，不迁移为真实录音。

## 9. P0 验收

- 完全不拍：8 拍结束泡泡救援；不会点击开始就自动成功。
- 正确跟拍：宠物逐步向外移动，可靠分析后成功。
- 快速乱拍/重复峰：不按总次数加力量，同一目标不能重复命中。
- 60% 命中边界：按 ceil(0.60 × N) 判断；N=8、N=12 分别检查。
- 平静留白与密集计划：同样命中比例具有相同终局力量，按目标时间而非等间隔评分。
- 实时暂定与最终分析不一致、噪声过大：不编造成功，录音仍可保留。
- 拒绝麦克风：可选明确标示的点击体验，不假称真实拍手。
- 中止、重试、改难度：停止旧时钟、释放资源，旧事件不污染新回合。
- 反馈、收藏、刷新与发奖：runId 幂等，planId 对应正确，原有本地作品不被覆盖。
- 真实音频模式必须在演示设备实测；模拟输入测试不等于麦克风验收。
